# native-ui: design

A library of components copied from OpenCode Desktop 2.2.5's own markup, for GUI plugins to import by relative path. It is not a plugin and is not registered. What it exports is in [README.md](README.md).

## Decisions

Reason for each copy, against the public components `ctx.ui` offers and the "no extension point" list in [host-architecture.md §8](../../../.claude/skills/opencode-gui-plugins/reference/host-architecture.md#8-public-and-internal-boundary).

- **Copy the host's markup, class names and data attributes** instead of drawing new look-alikes: the app's own CSS then styles them, so a theme or host update changes them together. `parity.spec.mjs` compares each component with the real element in the running app. The cost is that the copy tracks 2.2.5 and may break on an update.
- **Menu** (`src/menu.tsx`): `ctx.ui.Menu` exists but is a trigger-bound dropdown that cannot open at a point, so a point-anchored context menu (session rows) cannot use it. The host's `Menu.Content`, `Item` and `Separator` markup and the attributes Kobalte sets are copied. Roving focus, which Kobalte provides in the host, is reimplemented (`nextItem`, `highlight`). `data-expanded` is set after a frame so the host's menu CSS plays its enter.
- **Spinner** (`src/spinner.tsx`, `spinner-radar.ts`, `spin-phase.ts`): `ctx.ui` offers only `Loader`, which the host reserves for non-AI loading, so the Soft Radar dot grid and keyframes are copied. Spin phases are pinned while visible so several spinners stay in step; reduced motion shows a still frame.
- **Session tab rows, close and row-action buttons, popover, summary card, project avatar, clock icon**: tab rows have no extension point, and `ctx.ui` has no equivalent. Tab row actions and close have `transition: none`, like the host's `[data-slot=tab-close] > button`.
- **Header icon button** wraps `ctx.ui.IconButton` (public) and adds the pressed look, `aria-haspopup`, `aria-expanded` and `aria-controls` the host's header buttons carry.
- **`createHost(ctx.ui)`** keeps the setup owner, so components rendered later from an observer, timer or DOM event still find the plugin's Solid context.
- **Sharing by relative path**, not a package: a consumer bundles the source into its own build (`snooze-archive` does, via its `tsconfig` include). `snooze-archive/src/menu.ts` re-implements part of the menu, a known duplicate, not a decision.
- **Injected-message row** (`src/injected-message-row.tsx`, `injected-rows.tsx`, `injected-text.ts`, `anchor.ts`, `RobotIcon`; user decisions 2026-11-01, icon 2026-11-02): one component for a message the app injected into a session (a peer's, a monitor's, a scheduled run's). The host has no message-renderer registry, so `mountInjectedRows` decorates mounted `UserMessage` timeline rows (hides the host bubble, appends the row in the same frame via a `MutationObserver` on the timeline scroll regions only, nothing runs while no open session holds a message of that kind); each plugin passes the messages it owns. The header copies the host subagent row's markup values and its trailing slot (width, margin, opacity, translateX over 150ms `ease`; 18px wider on hover, 36px with the triangle), the triangle rotates like the host's collapsible arrow, and the header is held under the pointer through a toggle (`holdTop`: the host re-pins the timeline on any resize, which would carry the header away). The peer kind's icon is a drawn outline robot, which supersedes the mockup's dithered 5x5 grid (the host catalog has no agent glyph; its subagent row uses `task`). Evidence and numbers: [orchestrator-tools DESIGN](../orchestrator-tools/DESIGN.md) (peer row).
- **Injected-row spacing = a user turn's** (2026-11-02, two rounds of user feedback on the live app; measured in the harness against plain bubbles, the host subagent row and consecutive messages, 1300px and 640px, light and dark). The row stands in a `UserMessage` timeline row, so it takes the host user row's footprint: the bubble (37px) + 8px margin + the 20px hover-only copy/retry footer, laid out whether or not it shows = **65px** for the last message of a run, **37px** for one followed by another user message (a 4px `turn-gap` row between them). The header is 36px (13px/20px type, like the host subagent row; the bubble's line is 17px), so the row pads 29px below it, or 1px inside a run, and totals are exact: row top to the next text part's top is 89px for a plain bubble and for ours (65 to a tool-first reply), row top to next user row 41px; previous assistant footer to row top is the TurnGap's 16px on both. The visible gap under the pill is therefore 1px more than under a bubble (53 vs 52 to a text part, 29 vs 28 to a tool part): an accepted difference, the pill being 1px shorter. Round two ("gap seems too big", 72px row and 110px gap read off a screenshot) was not a double count: the screenshot was 2x pixels (36px pill = 72, 55px = 110, 15px footer gap = 30), and the 52px under a bubble is the host's own 28px reserve plus the 24px top margin a text part gets after a user turn. Nothing is counted twice because the host's bubble and footer are `display: none` inside an injected row. The reserve is `padding-bottom` on the row (a margin collapses out of the host's content box, which the virtualised timeline measures); the in-run rule is `[data-timeline-key^="user-message:"]:has(+ [data-timeline-key^="turn-gap:"] + [data-timeline-key^="user-message:"])`, one level of `:has` (nesting is invalid). The host subagent row's own rhythm in an assistant turn (8px above and below) is not the target: it is an assistant part, the injected row a user turn. Open row: 4px header-to-card, then the same trailing padding. The parity spec asserts the totals against a live plain bubble (`spacing-user-turn`).
  - Grey header kept when open: the preview stays in layout with `visibility: hidden`, so the header's box does not change (Δ0.00 in x, width and y per frame, measured) and the second click lands where the first did. The body is a card below the header, outside the click target, mounted only while open (no Markdown or text cost for closed rows).
  - Display text is the real content: `unescapeMarkup` undoes one level of the servers' wrapper escaping (`&amp;gt;` shows `&gt;`, what the command printed), no wrapper tags, no trailer.
  - No `cursor: pointer` (the app reserves it for links); `lint.mjs` forbids it outside `a` and `[role=link]`.
  - The action is a 24px ghost icon button from `ctx.ui.IconButton`; `ctx.ui` has no stop-square icon, so Stop and Cancel use the catalog `close`.
  - Not built: a height animation (the host's collapsibles are instant too).

## Composer chips (`chip-motion.ts`, `lane-chip.ts`, `lane-chip-rows.tsx`, `session-chip.tsx`, `chip-time.ts`)

Written against OpenCode Desktop 2.2.5; host sources are the `v2.2.5` tag (`packages/app/src/session/composer/`). Decisions (user, 2026-11-02): no subagents panel and no header button; lean into the host's own Background activity row and add chips of the same kind; one "N monitors" and one "N schedules" chip, each hidden at zero; a click opens a popover above the chip with a row per item and a Stop or Cancel action; scope is the items aimed at the session on screen.

- **The chip is the host's.** `ComposerPill` is the sanctioned registry for it (host-architecture §9). The host renders the capsule (`[data-composer-pill]`, `composer-lane.css`: 32px, 8px radius, raised surface, overlays, focus ring), the popover (`w-80`, 150ms `composer-pill-panel-in`) with `title` as its heading, its placement, focus and dismissal. Plugin pills sit in `[data-component="session-plugin-pills"]` (`gap-2`) in the lane `[data-component="session-composer-lane"]`, after the activity capsule and the todo pill, on the side away from the lane's aligned edge (`order-2`; `-order-2` when the setting is Right). Nothing is injected; there is no observer.
- **What the host does with motion: none for plugin pills.** A pill is inserted and removed in the frame `show` changes, and the row does not reflow smoothly; only the activity capsule fades in (`animate-in fade-in`, 150ms, only for work that starts while the session is open, none on exit). Measured by sampling at display rate (about 120Hz) the lane's pills for each add and remove. So the motion here is the plugin's, and each plugin does it alone with no coordination.
- **Motion (user asked for it).** The chip collapses its own box on the Web Animations clock: width, horizontal padding, border, `margin-inline: -4px` (half the lane's 8px gap on each side, so the gap goes with it), opacity 0 to 1 and `scale(0.97)`. 200ms, `cubic-bezier(0.23, 1, 0.32, 1)` (animation.md), `overflow: hidden` and `inert` while it runs, 150ms opacity only under reduced motion (`prefers-reduced-motion` or `:root[data-motion="reduce"]`). The flex row does the rest: every neighbour, the host's capsule and the other plugin's chip included, is moved by layout on every frame, so nothing needs to know about anything else. A chip alone in the host's pill container also gives the container's lane gap back (container margins). Tested at Left, Center and Right with a running subagent, a monitor and a schedule present.
- **Exit is the controller's job.** The host removes a pill the moment `show` returns nothing, so `show` reads a count the controller owns (`createLaneChip`); at zero it keeps the old count (and text) until the collapse ends, then lets go. A chip asked back while it leaves, or emptied while it enters, is reversed where it stands (`Animation.reverse`), and a count that arrives mid-move is shown after the move, with its own width ease ("1 monitor" to "2 monitors" is a letter wider). The end is the animation's `finish` event, with one backstop timer for a window the OS does not repaint.
- **Only a change the user watches moves.** `settle(session, count)` animates only when the count was already known in the same routing visit (`MountedSession.visit`); a session just opened, a switch or a first answer sets the chip at rest, as the host's capsule stays at rest on a switch.
- **Icons.** `ComposerPillView.icon` takes catalog names only and the catalog has no clock. Monitors use `outline-console` (the injected row's). Schedules name a placeholder catalog icon (`outline-rotate-clockwise`, `CLOCK_PLACEHOLDER`); `laneChipCss` hides its svg and draws the same clock as `ClockIcon` as the capsule's `::before`, in the same 14px box and colour, only inside our two chips (`:has(use[href$=...])`). Brittle against a host change to the sprite's href; a catalog clock would remove it.
- **Background activity setting: not followed, and it cannot be.** The setting (Hidden, Left, Center, Right) hides the host's activity capsule and sets the lane's alignment. Plugin pills ignore Hidden in 2.2.5: `SessionPluginPills` is rendered whatever the value, and `ctx` has no settings API. Hidden also yields the same lane alignment (`start`) as Left, so a plugin cannot tell them apart from the DOM either. Our chips therefore stay visible, at the left, when the setting is Hidden (observed). Left, Center and Right are honoured by the host's placement of every pill (alignment, popover placement `top-start`, `top`, `top-end`). Worth an upstream ask: pills following `backgroundActivity: "off"`.
- **Popover rows.** Two-line rows (name, muted status) on the host menu item's grid: 16px glyph, 8px gap, 13px type, name 530 like the activity panel's agent name, `--v2-overlay-simple-overlay-hover` on hover, a 28px minimum. They are not `menu-v2-item`s because that height is fixed. The action is the host's small `ghost-muted` `IconButton` (`outline-xmark`), revealed on hover or focus-within (always on touch, 44px). Plain list with real buttons: Tab reaches each action; Escape and focus return are the host popover's. A removed row leaves at once and focus moves to the neighbour's action; when the last item goes through the keyboard, focus lands in the prompt, as the host's capsule does.
- **Data, event driven.** Asked of the server half (`monitor.list`, `scheduler.pending`: names, states and numbers, never commands, output or prompts) for the session on screen when it changes, when its messages change (`messageSignature`: the last four messages' ids, completion times and part counts, so a wake, a notice or a finishing tool call), when the popover opens and after the user's own action. No interval anywhere. The one timer runs only while the popover is open and sleeps until the next displayed span (`span`, rounded up to the minute) changes (`nextChange`). A monitor or schedule that starts with no message in the target session (another session started it) shows when that session next changes, is switched to or has its popover opened; a server push (an RPC event) would close that gap and was left out as more machinery than the brief asked for.
- **Not built:** a chip per item; navigation to the session that started an item (the definition records the session it wakes, not who started it, and the scope is items aimed at the current session, so the target is always the one on screen); a chip in a subagent's session (the host shows no pills there).

### Popover rows against the host's activity panel

Measured one after the other (the two cannot be open together: opening one dismisses the other) with the same computed properties, harness 2.2.5: panel radius 10px, background, shadow, padding 4px and border equal; panel width 320px against `max-content`; row colour, radius and hover token equal (colour was `rgb(0,0,0)` against `rgb(22,22,22)` until the row took `--v2-text-text-base`); row height 40px against 28px (two lines by design); name weight 530 equal; status 13px equal. The capsule itself: `parity.spec.mjs` run `chip.parity.spec.mjs`, 410 PASS, 0 FAIL, 116 N/A (width and glyph size from the label and icon, the native capsule's own animations, the pressed state of a menu trigger against a popover trigger). Found by it: the host capsule transitions `all` 150ms and a plugin pill has no transition, so `laneChipCss` gives ours `transition-duration: 150ms`.

## Known gaps

- Module state: a module `WeakSet` in the header icon button. It is not owned by a plugin owner, so a Reload leaves the set behind.
- 20 tests for the exports (the injected row has its own, `anchor.ts` moved here with its tests); the parity spec covers the rest live.
- `demo/` is a separate GUI plugin used to exercise the components; it has a document-wide observer and is not part of the library.

## Performance

Measured through the injected-message row in [orchestrator-tools DESIGN](../orchestrator-tools/DESIGN.md#performance) (three plugins on one shared observer per window); the other components are not measured. The library registers nothing itself. Standing cost of what it exports: none at import: each spinner makes its own `ResizeObserver` and `IntersectionObserver` in its owner and disconnects them on cleanup; the keyframes are `spinnerCss`, registered by the consumer. Method and bars: [performance.md](../../../.claude/skills/opencode-gui-plugins/reference/performance.md).

| Scenario | Bare | With plugin | Delta | Bar | Result |
| --- | --- | --- | --- | --- | --- |
| idle (chips shown) | | | | zero callbacks | 20s: no setTimeout, setInterval or observer from the chips (one host timer); PASS |
| 10 session switches | | | | within 3% scripting | not measured |
