# native-ui: design

A library of components copied from OpenCode Desktop 2.2.5's own markup, for GUI plugins to import by relative path. It is not a plugin and is not registered. What it exports is in [README.md](README.md).

## Decisions

- **`humanizeLine`** (`src/humanize-line.ts`, 2026-11-03): the header preview of an injected row is reworded for reading; the card, the model's text and the event payload keep the raw line. Whole whitespace-delimited tokens only (after stripping `(`, `)`, `,` and the like, and a `key=` prefix): an ISO-8601 timestamp (`Z`, offset or none, ms ok) becomes "just now", "3m ago", "in 5m", then clock time today, "yesterday 20:24", "Nov 2, 20:24"; a snake_case status from a fixed list (`in_progress`, `timed_out`, `action_required`, ...) loses its underscore. Plain words are not listed (they already read fine). Tokens inside backticks and tokens holding `://` are skipped. Pure in (line, minute), memoised per line and minute (cache cleared at 400 entries); `minuteClock()` is one signal per plugin so a relative time moves on at most once a minute. `InjectedMessageRow` takes `previewTitle`, the raw line, as the header's `title` when the preview differs. The multi-line batch header stays as it was: first line plus `· N lines`.

Reason for each copy, against the public components `ctx.ui` offers and the "no extension point" list in [host-architecture.md §8](../../../.claude/skills/opencode-gui-plugins/reference/host-architecture.md#8-public-and-internal-boundary).

- **Copy the host's markup, class names and data attributes** instead of drawing new look-alikes: the app's own CSS then styles them, so a theme or host update changes them together. `parity.spec.mjs` compares each component with the real element in the running app. The cost is that the copy tracks 2.2.5 and may break on an update.
- **Menu** (`src/menu.tsx`): `ctx.ui.Menu` exists but is a trigger-bound dropdown that cannot open at a point, so a point-anchored context menu (session rows) cannot use it. The host's `Menu.Content`, `Item` and `Separator` markup and the attributes Kobalte sets are copied. Roving focus, which Kobalte provides in the host, is reimplemented (`nextItem`, `highlight`). `data-expanded` is set after a frame so the host's menu CSS plays its enter.
- **Spinner** (`src/spinner.tsx`, `spinner-radar.ts`, `spin-phase.ts`): `ctx.ui` offers only `Loader`, which the host reserves for non-AI loading, so the Soft Radar dot grid and keyframes are copied. Spin phases are pinned while visible so several spinners stay in step; reduced motion shows a still frame.
- **Session tab rows, close and row-action buttons, popover, summary card, project avatar, clock icon**: tab rows have no extension point, and `ctx.ui` has no equivalent. Tab row actions and close have `transition: none`, like the host's `[data-slot=tab-close] > button`.
- **Header icon button** wraps `ctx.ui.IconButton` (public) and adds the pressed look, `aria-haspopup`, `aria-expanded` and `aria-controls` the host's header buttons carry.
- **`createHost(ctx.ui)`** keeps the setup owner, so components rendered later from an observer, timer or DOM event still find the plugin's Solid context.
- **Sharing by relative path**, not a package: a consumer bundles the source into its own build (`snooze-archive` does, via its `tsconfig` include). `snooze-archive/src/menu.ts` re-implements part of the menu, a known duplicate, not a decision.
- **Injected-message row** (`src/injected-message-row.tsx`, `injected-rows.tsx`, `injected-text.ts`, `anchor.ts`, `RobotIcon`; user decisions 2026-11-01, icon 2026-11-02): one component for a message the app injected into a session (a peer's, a monitor's, a scheduled run's). The host has no message-renderer registry, so `mountInjectedRows` decorates mounted `UserMessage` timeline rows (hides the host bubble, appends the row in the same frame via a `MutationObserver` on the timeline scroll regions only, nothing runs while no open session holds a message of that kind); each plugin passes the messages it owns. The header copies the host subagent row's markup values and its trailing slot (width, margin, opacity, translateX over 150ms `ease`; 18px wider on hover, 36px with the triangle), the triangle rotates like the host's collapsible arrow, and the header is held under the pointer through a toggle (`holdTop`: the host re-pins the timeline on any resize, which would carry the header away). Held Δy 0.00 whenever the scroller has room below the header; closing a row within its body's height of the timeline's end cannot hold (the clamped `scrollTop` lowers the header by `scrollTop - newMax`), accepted: padding to make room would leave a gap above the next message ([orchestrator-tools DESIGN](../orchestrator-tools/DESIGN.md), "Header hold"). The peer kind's icon is a drawn outline robot, which supersedes the mockup's dithered 5x5 grid (the host catalog has no agent glyph; its subagent row uses `task`). Evidence and numbers: [orchestrator-tools DESIGN](../orchestrator-tools/DESIGN.md) (peer row).
- **Injected-row hover = the host subagent row's, long rows included** (2026-11-02, user: "the animation on this is wrong"; measured per frame in the harness, 120Hz, real pointer, host rows and ours side by side). Short rows already matched (+18px, 150ms `ease`); full-width rows did not. The host row is `max-width: calc(100% - 24px)` (672 of a 696 container); its head is `[info-main: flex 1 1 auto, min-width 0, overflow hidden, title + subtitle flex 0 0 auto][action slot at the row's end]` inside an 8px gap, and the slot's `margin-inline-start: 0 -> 2px`, `width: 0 -> 16px`. So at the cap the row does not grow: the clip box gives up 18px and cuts the text **mid-glyph, no ellipsis**, and the chevron stays on the row's right edge (1154 -> 1150, a 4px path, because the 16px chevron is centred in a slot that grows from the edge). Ours had the cap at 100% (696), a preview that shrank by 36px with an ellipsis sliding every frame, and the slot anchored to the preview, so the chevron started 18px outside the row and travelled 30px. Now: the head is `[icon][injected-main clip box][injected-tail]`, same cap, same margins (0 at rest, 2px open; the old -8px/-6px margins cancelled an 8px gap the host does keep, which made ours 8px narrower at rest and cut full-width text 8px closer to the slot), and the action rides the edge (the tail is end-aligned and the action slides 8px over the same 150ms, which gives the host's 4px path whatever the slot's width). **Ellipsis requirement superseded by the standing exact-parity rule: no ellipsis, as the host.** The title lost its 280px cap and ellipsis for the same reason. The expand triangle is ours alone: it makes the slot 34px (16 triangle + 2 gap + 16 action; 16px when the row has no action, `data-action` on the row), so an expandable row's clip box gives 36px against the host's 18px and a short expandable row grows 36px; rest widths and positions are the host's. The expandable test compares the clip box's content with its width at rest (width plus what the slot has taken), so the hover cannot flip a row between plain and expandable. Per frame, long hover-in/out, host vs ours (ours is the expandable row): row growth 0 vs 0, chevron from the right edge 8.0 -> 12.0 on both within 0.05px, clip edge from the right edge 20 on both at rest then 38 vs 56 settled (18 vs 36: the triangle), all curves on `ease` within 1.5% of travel; short rows: row growth, slot width, chevron and clip edge within 0.25px every frame (sampling phase). Before: chevron travelled 30px (1204 -> 1174), starting 18px outside the row's right edge; row 696 against the host's 672; preview shrank 36px with a sliding ellipsis. Checked also on monitor and scheduler rows (shared component), the open state (header y unchanged, slot stays open), 640 and 480px viewports and dark. `orchestrator-tools/parity.spec.mjs` has the long-row per-frame check (`long-row-hover`).
- **Injected-row spacing = a user turn's** (2026-11-02, two rounds of user feedback on the live app; measured in the harness against plain bubbles, the host subagent row and consecutive messages, 1300px and 640px, light and dark). The row stands in a `UserMessage` timeline row, so it takes the host user row's footprint: the bubble (37px) + 8px margin + the 20px hover-only copy/retry footer, laid out whether or not it shows = **65px** for the last message of a run, **37px** for one followed by another user message (a 4px `turn-gap` row between them). The header is 36px (13px/20px type, like the host subagent row; the bubble's line is 17px), so the row pads 29px below it, or 1px inside a run, and totals are exact: row top to the next text part's top is 89px for a plain bubble and for ours (65 to a tool-first reply), row top to next user row 41px; previous assistant footer to row top is the TurnGap's 16px on both. The visible gap under the pill is therefore 1px more than under a bubble (53 vs 52 to a text part, 29 vs 28 to a tool part): an accepted difference, the pill being 1px shorter. Round two ("gap seems too big", 72px row and 110px gap read off a screenshot) was not a double count: the screenshot was 2x pixels (36px pill = 72, 55px = 110, 15px footer gap = 30), and the 52px under a bubble is the host's own 28px reserve plus the 24px top margin a text part gets after a user turn. Nothing is counted twice because the host's bubble and footer are `display: none` inside an injected row. The reserve is `padding-bottom` on the row (a margin collapses out of the host's content box, which the virtualised timeline measures); the in-run rule is `[data-timeline-key^="user-message:"]:has(+ [data-timeline-key^="turn-gap:"] + [data-timeline-key^="user-message:"])`, one level of `:has` (nesting is invalid). The host subagent row's own rhythm in an assistant turn (8px above and below) is not the target: it is an assistant part, the injected row a user turn. Open row: 4px header-to-card, then the same trailing padding. The parity spec asserts the totals against a live plain bubble (`spacing-user-turn`).
  - Grey header kept when open: the preview stays in layout with `visibility: hidden`, so the header's box does not change (Δ0.00 in x, width and y per frame, measured) and the second click lands where the first did. The body is a card below the header, outside the click target, mounted only while open (no Markdown or text cost for closed rows).
  - Display text is the real content: `unescapeMarkup` undoes one level of the servers' wrapper escaping (`&amp;gt;` shows `&gt;`, what the command printed), no wrapper tags, no trailer.
  - No `cursor: pointer` (the app reserves it for links); `lint.mjs` forbids it outside `a` and `[role=link]`.
  - The action is a 24px ghost icon button from `ctx.ui.IconButton`; `ctx.ui` has no stop-square icon, so Stop and Cancel use the catalog `close`.
  - Not built: a height animation (the host's collapsibles are instant too).

## Composer chips (`chip-motion.ts`, `lane-chip.ts`, `lane-chip-rows.tsx`, `session-chip.tsx`, `chip-time.ts`)

Written against OpenCode Desktop 2.2.5; host sources are the `v2.2.5` tag (`packages/app/src/session/composer/`). Decisions (user, 2026-11-02): no subagents panel and no header button; lean into the host's own Background activity row and add chips of the same kind; one "N monitors" and one "N schedules" chip, each hidden at zero; a click opens a popover above the chip with a row per item and a Stop or Cancel action; scope is the items aimed at the session on screen.

- **The chip is the host's.** `ComposerPill` is the sanctioned registry for it (host-architecture §9). The host renders the capsule (`[data-composer-pill]`, `composer-lane.css`: 32px, 8px radius, raised surface, overlays, focus ring), the popover (`w-80`, 150ms `composer-pill-panel-in`, `title` as its heading: all three overridden by `laneChipCss`, see Popover rows), its placement, focus and dismissal. Plugin pills sit in `[data-component="session-plugin-pills"]` (`gap-2`) in the lane `[data-component="session-composer-lane"]`, after the activity capsule and the todo pill, on the side away from the lane's aligned edge (`order-2`; `-order-2` when the setting is Right). Nothing is injected; there is no observer.
- **The whole header toggles; only the action button does its own thing** (2026-11-02, user: "I can't click the expand button to expand"). The head is `[trigger][icon][clip box][tail]`: the trigger is an `inset: 0` button first in the head, and every later part is painted above it (positioned or not), so a click reaches the trigger only if the part under the pointer has `pointer-events: none`. Icon, clip box (title, preview) and arrow had it; the tail slot did not, once the restructure (14fcad3) made it a real 16-34px box over the triangle, so a click on the triangle hit the invisible slot and nothing happened, hovered or not, open or closed, on every kind. Fix: the tail has `pointer-events: none` and the action button inside it `pointer-events: auto` (it keeps its own action and does not toggle, as it is outside the trigger). Checked with real CDP clicks (`mousePressed`/`mouseReleased` plus `elementFromPoint`) on padding (left, top), icon, title, preview, the clip box's right edge, the gap before the slot and the triangle, closed and open, at rest and hovered, long and short, peer, monitor and scheduler: all hit `injected-trigger` and toggle (before: the triangle hit `injected-tail`, 0 of 20 toggled); Enter and Space on the focused trigger toggle; a click in the open card does not; Open session does its own action without toggling. Guarded by a unit test on the stylesheet (each part passes the pointer through, only `.injected-action` takes it) and by `click-targets` in the orchestrator-tools `parity.spec.mjs`.
- **A clipped injected row fades at the clip edge, as the host's sidebar tab titles do** (2026-11-02, user: "there's no fade on full width, it should fade like the sidebar icons do, not be a block"). The host's subagent row has no fade (hard mid-glyph cut), so the mechanism is copied from the tab-title rule in the host stylesheet (`[data-titlebar-tab][data-title-overflow=true] [data-slot=tab-link]`): `mask-image: linear-gradient(to right, black 0, black calc(100% - offset - 16px), transparent calc(100% - offset), transparent 100%)`, a 16px linear ramp, only while the text overflows, not animated. Offset is 0 because the mask is on the clip box itself, whose edge is where the text is cut, and the percentages follow that edge when the slot opens on hover (18px or 36px earlier, no jump, no JS per frame). Overflow is `data-clipped` on the row, set by the row's existing ResizeObserver (now run for every row, `more` ones included; before, only rows whose body is the preview). A row that fits has no mask. Checked in the harness at rest and hovered: ramp visible, clip edge, row width and chevron path unchanged per frame (`measure2`/`cmp`, `long-row-hover` passes).
- **What the host does with motion: none for plugin pills.** A pill is inserted and removed in the frame `show` changes, and the row does not reflow smoothly; only the activity capsule fades in (`animate-in fade-in`, 150ms, only for work that starts while the session is open, none on exit). Measured by sampling at display rate (about 120Hz) the lane's pills for each add and remove. So the motion here is the plugin's, and each plugin does it alone with no coordination.
- **Motion (user asked for it).** The chip collapses its own box on the Web Animations clock: width, horizontal padding, border, `margin-inline: -4px` (half the lane's 8px gap on each side, so the gap goes with it), opacity 0 to 1 and `scale(0.97)`. 200ms, `cubic-bezier(0.23, 1, 0.32, 1)` (animation.md), `overflow: hidden` and `inert` while it runs, 150ms opacity only under reduced motion (`prefers-reduced-motion` or `:root[data-motion="reduce"]`). The flex row does the rest: every neighbour, the host's capsule and the other plugin's chip included, is moved by layout on every frame, so nothing needs to know about anything else. A chip alone in the host's pill container also gives the container's lane gap back (container margins). Tested at Left, Center and Right with a running subagent, a monitor and a schedule present.
- **Exit is the controller's job.** The host removes a pill the moment `show` returns nothing, so `show` reads a count the controller owns (`createLaneChip`); at zero it keeps the old count (and text) until the collapse ends, then lets go. A chip asked back while it leaves, or emptied while it enters, is reversed where it stands (`Animation.reverse`), and a count that arrives mid-move is shown after the move, with its own width ease ("1 monitor" to "2 monitors" is a letter wider). The end is the animation's `finish` event, with one backstop timer for a window the OS does not repaint.
- **Only a change the user watches moves.** `settle(session, count)` animates only when the count was already known in the same routing visit (`MountedSession.visit`); a session just opened, a switch or a first answer sets the chip at rest, as the host's capsule stays at rest on a switch.
- **Icons.** `ComposerPillView.icon` takes catalog names only and the catalog has neither a clock nor an ECG trace. Monitors name `outline-wave-audio` (live) or `outline-dots` (every monitor paused) and `heartbeatChipCss` hides that svg and draws the heartbeat (next section). Schedules name a placeholder catalog icon (`outline-rotate-clockwise`, `CLOCK_PLACEHOLDER`); `laneChipCss` hides its svg and draws the same clock as `ClockIcon` as the capsule's `::before`, in the same 14px box and colour, only inside our two chips (`:has(use[href$=...])`). Brittle against a host change to the sprite's href; a catalog clock would remove it.
- **Background activity setting: not followed, and it cannot be.** The setting (Hidden, Left, Center, Right) hides the host's activity capsule and sets the lane's alignment. Plugin pills ignore Hidden in 2.2.5: `SessionPluginPills` is rendered whatever the value, and `ctx` has no settings API. Hidden also yields the same lane alignment (`start`) as Left, so a plugin cannot tell them apart from the DOM either. Our chips therefore stay visible, at the left, when the setting is Hidden (observed). Left, Center and Right are honoured by the host's placement of every pill (alignment, popover placement `top-start`, `top`, `top-end`). Worth an upstream ask: pills following `backgroundActivity: "off"`.
- **Popover rows = the host's "1 subagent" popover, native one-line rows** (2026-11-02, user decisions after the measurement report `/tmp/chipmeasure/REPORT.md`; supersedes the two-line row and the host-heading decisions). Rows are 28px, `padding: 0 6px`, `column-gap: 8px`: a 16px glyph, the name (13px/530, ellipsis when long: the host's own summary truncates the same way), and the status as the muted 11px tabular trailing text where the host shows the elapsed time. Hover or focus hides the status (`visibility`, as the host's elapsed does) and shows the action in its place, a 20px small `ghost-muted` `IconButton` with a 14px glyph (the action uses `opacity`, not `visibility`: a button that is not rendered cannot take the focus the arrow keys give it). Monitors show the host's live dot-grid spinner (`ProgressSpinner`; every listed monitor is running); schedules keep the drawn clock, no spinner. No count heading: `laneChipCss` hides the host's `title` line (`title` stays as the dialog's accessible name and the chip's `aria-label`). Panel, matching the host's menu content: no open animation (`animation: none`; the host's `composer-pill-panel-in` is overridden with `[data-composer-pill-panel][data-slot=...]` for specificity), `width: max-content`, `min-width: 240px`, `max-width: min(360px, 100vw - 56px)`, `max-height: 270px` with the panel as the scroll owner (rows are `flex: none`, so 11 or 12 rows scroll at 269px instead of squashing), positioner `z-index: 60 !important` (the host sets `z-index: auto` inline), rows `cursor: default; user-select: none`.
- **Popover keyboard = the host menu's, one deviation.** Focus moves into the list on open: a keyboard open (the last input before the open was a key, tracked by a capture listener in `createSessionChip`; the host does not say) lands on the first row, a pointer open on the list itself with nothing highlighted, like the host's menu. Up and Down (and Home, End) move between rows, the highlight is the host's hover token on the focused row. Tab is trapped (`preventDefault`: with one list there is nowhere else to go, which is what the host's focus trap amounts to, 5 or 6 of 6 presses stay inside, measured). Escape is the host popover's: closes and returns focus to the chip. **Stop reachable by keyboard, decided:** the row has no primary action (the host's row opens the subagent, ours has nothing to open), so Enter on a row does nothing, and a Tab-focusable Stop would break the single tab stop. The action is `tabindex=-1` like the host's; ArrowRight moves from a row to its action, ArrowLeft back, Up and Down then move between actions, Enter or Space presses. The host's Stop is unreachable by keyboard, so this is a deliberate addition, with no Tab stop and no destructive Enter on a freshly opened list. After an action focus moves to the neighbouring row (its action when the keyboard pressed it) once the list has updated: rows are keyed by id, not object (the list was rebuilt on every refresh and every minute tick, which dropped focus to the body: that was the bug), and the refocus waits a microtask. When the last item goes, focus goes to the prompt, for the mouse as well as the keyboard, as the host's does.
- **Popover: upstream asks, not hacked.** (1) The chip opens on `pointerdown` and shows the open surface while pressed; a pill opens on click and shows the pressed overlay (the one remaining chip-state difference). (2) `role="menu"` / `aria-haspopup="menu"` for pills with a list; ours is a `dialog` containing a list. (3) The host menu is modal: the first click outside only closes it and is swallowed; a pill's popover lets the click through, so it opens the other chip. (4) Clicking the prompt while it is open returns focus to the chip in the host, focuses the prompt here.
- **Data, event driven.** Asked of the server half (`monitor.list`, `scheduler.pending`: names, states and numbers, never commands, output or prompts) for the session on screen when it changes, when its messages change (`messageSignature`: the last four messages' ids, completion times and part counts, so a wake, a notice or a finishing tool call), when the popover opens and after the user's own action. No interval anywhere. The one timer runs only while the popover is open and sleeps until the next displayed span (`span`, rounded up to the minute) changes (`nextChange`). A monitor or schedule that starts with no message in the target session (another session started it) shows when that session next changes, is switched to or has its popover opened; a server push (an RPC event) would close that gap and was left out as more machinery than the brief asked for.
- **Not built:** a chip per item; navigation to the session that started an item (the definition records the session it wakes, not who started it, and the scope is items aimed at the current session, so the target is always the one on screen); a chip in a subagent's session (the host shows no pills there).

### Popover rows against the host's activity panel

Measured side by side in the harness (2.2.5, real pointer and keys, light and dark, 1, 5, 9, 11 and 12 items, long names; `cmp.mjs`, `flow2.mjs`, `kb2.mjs` under the report's method), host "N subagents" against "N monitors" and "N schedules". Equal on the computed properties listed: panel width (max-content, 240 min, 360 clamp), min and max width, max-height 270 and scroll owner (11 rows: 269 client, 316 scroll on both), padding, radius, background (light 250, dark 36), shadow, animation none and opacity 1 on every frame after the click, positioner z-index 60, row height 28 (all 12 rows, no squash), padding, radius, hover background (0.04, dark 0.06), cursor, user-select, column gap, name 13px/530 and colour, trailing text 11px/440 muted, hidden on hover, action 20px with a 14px glyph, revealed on hover. Keyboard: pointer open focuses the panel/list with nothing highlighted and ArrowDown highlights rows 0, 1, 2 and ArrowUp goes back, on both; keyboard open highlights row 0, on both; Escape closes and focuses the chip, on both. Differences left: the name truncates here (the host's name is `shrink-0` and its summary truncates); the host's Tab left the menu once in six presses in light and never in dark, ours never does; the action is `opacity: 0` at rest (the host's is `visibility: hidden`), visually the same; a mouse Stop leaves focus on the body in the host and on the neighbour row here; the host's single Stop is not keyboard reachable. The capsule itself: `parity.spec.mjs` run `chip.parity.spec.mjs`, 411 PASS, 0 FAIL, 115 N/A (width and glyph size from the label and icon, the native capsule's own animations, the pressed state of a menu trigger against a popover trigger, and the two popover elements, which cannot be open together). Found by it: the host capsule transitions `all` 150ms and a plugin pill has no transition, so `laneChipCss` gives ours `transition-duration: 150ms`.

## Heartbeat icon (`heartbeat.ts`, `HeartbeatIcon`)

Decisions (user, 2026-11-03): the monitors' `>_` becomes an animated ECG heartbeat while a monitor is active, and a heartbeat that flattens into a straight line over ~300ms and stays still and muted once it is done. One shared icon, drawn here like `RobotIcon`, for the composer chip, the popover rows and the timeline row.

- **History of the motion** (each round the user's reason). v1: a simple trace (flat, one up spike, one down spike, a small return, flat) on two stacked layers, the whole trace flashing with the beat by opacity; the user: "very close". v2: "tighten it up so it's thinner but more obvious as it's going through" meant the motion (a crisper, more legible pass), not a shorter icon; tried a clip-path window sweeping the trace, then three trace thirds pulsing in turn on a 0.9px trace. v3: "more of a dot": a 3px bright dot with a halo and two trailing dots ran a P-QRS-T trace. v4: the user found the dot "too prominent and not world class"; a soft 7px band of light glided along the P-QRS-T (transform and opacity, stencil on the chip). v5: the user found v4's line "too complex, it was actually very close with your first iteration, I just needed slight refinement": v1's simple trace and v1's whole-trace opacity flash, refined. **v6 (this): the user on v5, "now we just need to make it more realistic: not a pulse but something that follows the line, in the chips for example"**, so v6 is v5's simple trace (geometry, 16px box and chip parity unchanged) with v4's travelling light, refined to a head with a fading tail like a heart-rate monitor's sweep. A whole-trace pulse is what the user asked to move away from, and it cannot follow a line; the v4 P-QRS-T stays out (the user found the line, not the band, too complex).
- **Drawing.** `M1.5 8H4.5L6 4L8 12L9.75 6.5L10.75 8H14.5` in the 16px box: `outline-*` style, 0.9px stroke (v1: 1px), round caps and joins, baseline y=8. The up spike is 4 above the baseline and the down spike 4 below (v1: 3.5 and 4), so the ink is centred on the baseline: **13.88 x 8.88 px of ink on the chip, centre (17.50, 16.00) in the capsule, the schedules clock chip's centre to 0.00 px** (8x frames, light and dark), label at +32.50, capsule 108.02 x 32 (measured on v6, equal to v5). The ink is as long as v1's 13px (v1's chip drew it in a 14px box, 11.4px of ink; the glyph box is now 16px, centred on the 14px, 10px-inset slot the catalog svg had: left 9px, it overhangs the slot by 1px each side, inside the 8px gap before the label). A 0.9px stroke at 1x straddles two pixel rows on the baseline (0.45 each); the baseline stays on y=8 because moving it by half a pixel would move the ink off the schedules chip's centre.
- **The sweep.** One band of light, `HEARTBEAT_BAND` = 9px wide, `height: 16px`, painted as a gradient of the base icon token whose **head is the sharp right edge** (full colour at 95%, gone by 100%, 0.45px) and whose **tail is long and soft** (90% at 90%, 55% at 70%, 26% at 45%, 9% at 20%, nothing at the left edge), so it reads as a head with a comet-like trail and never as a dot or a halo; it is over the muted trace only through the stroke (a mask on rows, a stencil on the chip), so no light exists outside the stroke. Moved by `transform: translateX()` and faded by `opacity`, nothing else, on one `@keyframes heartbeat-sweep` of 2.4s: the head enters at the stroke's left end (x=1.5, 90ms, fade in), crosses the first flat slowly (x 1.5 to 4.5 in 250ms, 12 px/s), goes through the spikes quicker (4.5 to 10.75 in 330ms, 19 px/s), relaxes to the end (10.75 to 14.5 in 250ms, 15 px/s), then leaves past the right end over 220ms ease-out while the light fades out (so it never cuts), 1.14s in all, then 1.26s of rest. Per-segment `animation-timing-function` on the stops; the segments are linear (a segment eased to a standstill and then restarted visibly jolted in round 1). Peak opacity 0.96: **peak against the resting muted trace 2.75:1 in light and 2.71:1 in dark** (measured on the pixels: rest 128 grey against 61 in light and 215 in dark; the base token at full opacity is 2.84 and 2.88). The trace keeps the muted token; nothing else is painted.
- **Tuning rounds** (8x seeked frames, 12 over the sweep, chip and row, light and dark; real-time capture of the chip at 2x; each verified against the computed transform). Round 1 (W=8, constant-ish speeds with ease-in-out first segment, peak 1.0, a short tail): it follows the stroke, but the tail was short and the first flat's ease-in-out ended near a standstill before the spikes (a jolt); contrast 2.84 / 2.88, a little hard in light. Round 2 (W=9, linear segments at 12, 19 and 15 px/s, a longer tail, peak 0.9): smoother and calmer; contrast 2.54 / 2.59, at the low end of the 2.5 to 3.2 target. Round 3 (shipped: peak 0.96, tail stops lifted a little, head full colour at 95%): contrast 2.75 / 2.71, the head still crisp at 1x and 2x, the trail reads across the flat, the spike and the return; the head in the pixels is within 0.43 px (light) and 0.46 px (dark) of the computed position on every full-opacity frame, 0 retries. Not tried: a longer band (9px is the most the chip's stencil can take: it would start outside the capsule's left edge) and a slower sweep (1.14s of a 2.4s loop already reads as a sweep with a calm rest).
- **Rows** (`HeartbeatIcon`: popover rows, the timeline's wake rows, collapsed and expanded): a `<span data-icon="heartbeat">` of 16x16 with `<b>` (the trace: a mask over the muted colour) holding `<i>` (the band; the mask clips it to the stroke) and `<u>` (the flat line). `live` sweeps, `still` is the trace at rest (reduced motion and a running monitor's older wakes), `flat` is the end state. Only the newest wake of a running monitor is `live`: of 15 mounted wake rows, 5 swept and 10 were still (verified in the harness, with the ended monitor's rows flat).
- **Chip.** The capsule is the host's, so no child can be added; it holds the catalog `svg` and its label `span`, and each has pseudo-elements. `heartbeatChipCss` hides the placeholder glyph's `use` and turns the `svg` into a flat muted plane in the 16px box, the capsule's `::before` into the band, its `::after` into a **stencil** (the capsule's own background, `inherit`, with a trace-shaped hole by `mask-composite: exclude`) over both, and the label's `::before` into the flat line. The pixel is `(1 - a) capsule + a (muted plus band)` with `a` the trace's coverage; a stencil over a masked trace would multiply the anti-aliased edge by itself and thin the 0.9px stroke. The stencil takes the capsule's hover, pressed and expanded backgrounds with it and runs from the capsule's left edge (the band starts 9px left of the glyph box) to where the label starts (32px), 1px taller each side than the plane. Only inside our two placeholder pills (`:has(use[href$=...])`).
- **Done = the trace squashes onto the baseline** (300ms). Going to `flat`: the trace (rows: `<b>`; chip: the plane and the stencil together) goes `scale: 1 1` to `1 0` about the baseline over 300ms on `cubic-bezier(0.25, 0.7, 0.3, 1)` (the host's 0.23,1,0.32,1 is 90% done in 100ms and the collapse would not be seen) while the flat line fades in; `display` is held for 320ms with `allow-discrete` so the squash is seen. The light stops at once (`display: none`; Chrome starts a transition from the value in the style without animations, so an animated light cannot be faded out without `animation-composition`, which a loop must not use). Nothing animates once settled (0 animations in the flat state). Failed or crashed monitors use the same flat line.
- **Reduced motion.** `prefers-reduced-motion` and `:root[data-motion="reduce"]`: the trace at rest (the chip's `svg` becomes the masked trace, the band and stencil are hidden), nothing animating (0 running sweeps, back to 6 when turned off, both switches), the squash instant. The trace and the flat line already say live and done by shape.
- **One clock.** Every instance runs the same keyframes and is pinned to the document timeline origin (`syncHeartbeats`: one capture listener on `animationstart`, matched by the animation's name), so every icon is in phase (measured on 6 live icons: one `startTime`, 0, and a `currentTime` spread of 0).
- **Why not the earlier motions** (measured, total CPU, renderer + GPU ms/s, popover open): v2's `clip-path: inset()` window 75 + 150 (x1) and 78 + 222 (x6), a re-raster every frame (709 raster tasks in 6s against none; the same with a `background-image` trace and with `will-change: clip-path`); an animated `mask-position` or `@property` gradient repaints on the main thread; v3's dot needed three animations per icon (18 shut, 33 open); v4's P-QRS-T was too complex for the user. v5's whole-trace flash was the cheapest and cannot travel. Things learned that still hold: a masked layer's `transform` and `opacity` are the only motion the compositor takes without re-rasterising; a stencil over an already masked trace multiplies the stroke's anti-aliased edge (a x a) and thins a 0.9px stroke; `animation-composition: add` on a looping animation forces per-frame style recalcs; Chrome starts a CSS transition from the value in the style *without* animations, so removing an animation snaps the property.
- **Where the heartbeat appears (audit, 2026-11-03).** (1) Composer chip: the stencil implementation above. (2) Popover rows: the row implementation, 28px rows and the 16px slot unchanged (measured 28 and 16 on all rows). (3) The inline timeline wake row (`InjectedMessageRow`'s icon slot), collapsed and expanded, light and dark: the same `HeartbeatIcon` (`media/heartbeat-inline-rows.png`: two ended wakes flat, an older wake of a running monitor still, its newest wake sweeping). (4) The monitor tool calls in the timeline (`monitor.start`, `monitor.list`, `monitor.stop`): **not done.** The tools are Code Mode tools, so the host renders them as its own "Used N Execute" group, with `monitor.start` and so on as the code text inside an `Execute` row and the host's `code-slash` glyph; a plugin's GUI half has three slots (`session.header`, `session.location.menu`, `session.panel.end`) and no tool-part renderer or icon slot, and the only route is rewriting the DOM of the host's tool row, which orchestrator-tools' DESIGN skipped for the same reason (`media/heartbeat-tool-rows.png` shows what the host draws). (5) Others: the toast and the notification for monitor events keep the shared kind glyphs (`KIND_GLYPH`, unchanged on purpose); the tab marks for a monitor that ended or restarted are the notifications plugin's one-off event marks (a kind glyph coloured by severity, gone when the session is opened), not a live indicator; a "this session has a running monitor" mark in the tab's status slot would be a new pattern (a standing animation per tab, no precedent in the host or the plugins), so none was added; the Settings > Notifications "Mark" column is a toggle per kind, with no icon of ours. No text or markdown mention draws an icon.
- **Evidence** (`media/`): `heartbeat-sweep-frames.png` (12 frames at 100ms over the sweep, 8x, chip and row, light and dark), `heartbeat-sweep-done.png` (the 300ms flatten, 8 frames, chip and row, light and dark), `heartbeat-sweep-realtime.png` (the chip captured in real time at 2x over one sweep: how it reads at actual size), `heartbeat-compare-8x.png` and `heartbeat-compare-2x.png` (v1, v4, v5 and v6 over the same 1.1s: the icon at 8x, with v6 in dark as well, and the chip at 2x), `heartbeat-inline-rows.png` (the timeline wake rows, collapsed and expanded, light and dark), `heartbeat-tool-rows.png` (the host's own rows for the monitor tool calls).
- **Pixel checks.** Lit pixels outside the stroke, by diffing each frame against the same frame with the band hidden (the stencil and plane kept): **0 on the chip** in rest, hover, pressed and expanded, light and dark, at 300, 500, 700 and 900ms (740 to 5,111 lit pixels each; the backgrounds 255, 245, 235, 36, 49 and 58); **0 on the popover row and on the timeline row**, light and dark, at the same four times (739 to 5,111 lit). Each frame was retried until it differed from the band-hidden frame (0 retries in the final runs). Reduced motion against the plain trace: at most 1/255 apart.
- **Cost** (harness 120 Hz, 1300x900, 10s windows; chip + 5 running timeline rows, + 5 popover rows when open; total CPU ms/s, renderer + GPU; two runs): **v6 shut 49-63 + 169-178 (6 animations), open 47-51 + 212-229 (11)**, nothing animating 0.5 + 1.2 (one 15 + 1.4 first sample on repeat, a one-off), long tasks 0. Against v5 (shut 42-63 + 122, open 35-43 + 104-126) the GPU cost is about 1.4x to 2x, the renderer's equal; against v4 (shut 60-75 + 190, open 49-51 + 210) it is the same. The travelling light is the same compositor work as v4's band; a whole-trace opacity flash is cheaper and cannot follow a line. The recalcs (38-40 per 10s while the popover has never been opened, then 0) are the host's: any animation on the page triggers them until the popover has been opened once.

- **Not changed.** The notifications plugin's kind glyphs (`KIND_GLYPH`).

## Known gaps

- Module state: a module `WeakSet` in the header icon button. It is not owned by a plugin owner, so a Reload leaves the set behind.
