# shell-handoff: design

Server-only plugin for OpenCode Desktop 2.2.5. No tools, no GUI.

## Decisions

- **Record, hand off, tell; never re-run** (2026-11-04, user). Recorded commands are data: nothing in this package executes, evaluates or replays a stored command, and the handoff file and notice say so. Re-running is the model's or the user's decision, made with the redacted text in front of them. A security decision as much as a scope one: a command from an earlier turn may no longer be safe or wanted, and a restart is not a reason to run it unseen.
- **What counts as a background job.** The result of a `shell` call whose metadata says `status: "running"` with a `shellID` (the host's own mark for a job that left the foreground). That covers `background: true` and a foreground command moved to the background after its timeout. `execute.after` is the only hook with the shell id. A foreground command costs one string comparison.
- **The host's events fill in what the tool call lacks.** `shell.created` carries cwd, the output file, the start time and the session. It arrives *after* `execute.after` (measured in the harness), so the record is written from the call and updated when the event comes; if the event never comes, cwd falls back to `workdir`. `shell.exited` / `shell.deleted` remove the record. `ctx.shell.hook("create.before")` has no session or id and is not needed.
- **A killed job keeps its record for 5 s.** The shutdown kill produces `shell.exited` with status `killed` before the process dies; removing the record then would lose exactly the case this plugin exists for. A manual kill leaves the process alive, the one-shot timer fires, and the record goes. Other exits remove it at once. The timer is unref'd and cancelled on dispose.
- **A restart is a new boot id.** `boot.ts` keeps `pid:start-time` of the service process on `globalThis` under `Symbol.for(...)`, as monitor's handoff does. A hot reload reloads the module inside the same process and sees the same id (nothing reported); a restart is a new process (everything recorded under another id is lost). Each record stores the boot id it was written under. The new boot's start time is also the loss time, so "ran about N" does not include the time until the project loaded.
- **Reconcile without polling.** `experimental.idle` lists the shell jobs still running; when a session idles, its recorded jobs that are not listed have finished and are dropped. The hook is experimental, so it only tidies stale records (a job that ended while the plugin was reloading); the events remain the main path. No endpoint is polled: `ctx` offers no HTTP client, and the hook plus the events cover it.
- **One instance per location, one shared storage.** The service loads the plugin once per project directory (measured: three instances in one process), every instance receives every event, tool hooks run only in the session's instance, and storage is one namespace per plugin. A record therefore carries its `location` and each instance restores and reports only its own, or one lost job would be reported once per instance. A pending notice is keyed by session and also carries the location. Consequence: a project is reported when it loads after the restart.
- **Notice delivery is `steer` with `resume: false`** (changed from the brief's `queue`, 2026-11-04). Measured in the harness: `queue` + `resume:false` delivers after the next turn and *starts another turn* to answer it (two model requests, an unprompted reply); `steer` + `resume:false` sits in the inbox and arrives in front of the next prompt (one request), which is what the host's own restart notice does. A notice that cannot be delivered (host not ready, session gone) is stored under `notice/<session>` and retried at the next setup and at the next `session.execution.started` of that session; a missing session drops it.
- **File layout.** `~/.local/share/opencode/shell-handoff/<sessionID>.md` (or `$XDG_DATA_HOME/opencode/...`, next to the host's `shell/` directory; the harness's private data dir in tests). Directory 0700, file 0600, written to a temp name and renamed. One file per session, a header and one `## Restart` section per restart, newest first, oldest sections dropped past 50 KB, files untouched for `retentionDays` pruned at setup. The session id is checked against `[A-Za-z0-9_-]` before it becomes a path.
- **Redaction happens before anything is stored.** The record holds the redacted command, the file and the notice use the same text, and parsing a stored record redacts it again (defence in depth). `redact.ts` is pattern based because, unlike blindfold, nothing here knows the secret values. It errs toward hiding (a redacted word costs a guess, a leak costs more). It cannot reach the host's own cancel notice, which prints the raw command (an upstream ask).
- **Notification** is optional and uses the hub's generic channel: an RPC event `notify` on the plugin's own rpc id, which the `notifications` plugin reads for any id (`rpc.<id>.notify`). Kind `info`, severity warning, key per boot, target the session when one session lost jobs. Without the hub nothing is heard and nothing falls back; the GUI-side fallback toast belongs to GUI halves. The session notice and the file do not depend on it.
- **Bounded.** `maxRecords` (200, oldest first), TTL `retentionDays` (7), `shell.created` memory capped at 300 entries, 5 jobs in the notice, 2000 characters per command in the file, 50 KB per file. Malformed, foreign (key mismatch) or expired stored entries are ignored and removed.
- **No pid.** The brief hoped for a pid to detect jobs that survived a crash. The host's job info has none for tool jobs (`pid` is absent in 2.2.5), so there is no liveness check.

## Verified in the private harness

Stub model calling the `shell` tool, the harness's own service restarted (never the user's): the host's cancel notice and this plugin's notice both reach the model on the next turn (one request), the handoff file has command, cwd, duration and ids (0600/0700), a seeded fake token and password are redacted everywhere this plugin writes, a hot reload (touching `dist`) and a second restart report nothing, and a job that finished produces nothing.
