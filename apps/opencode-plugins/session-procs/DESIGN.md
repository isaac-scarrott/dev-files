# session-procs: design

Server-only plugin for OpenCode Desktop 2.3.0. No tools, no GUI.

## Decisions

- **Only what the host spawned is ever touched** (Isaac, 2026-11-16). A process group is tracked only when a `shell.created` event was matched to it: the host's own pid (2.3.0 publishes `info.pid`), that process leading its own group (`pid == pgid`), a parent that is the service or the `opencode-pty daemon` the service runs, our uid, and a start time within 2 s of `info.time.started`. No match, or two matches (identical commands started together), means not tracked: a wrong pgid is a wrong kill, an untracked `&` server is only a leftover. The never-killed list (user terminals, `!command`, MCP servers, the pty daemon, the service and ancestors, monitors, other sessions, other uids, reused pids) falls out of that one rule plus `verified()` at kill time.
- **The spec's argv check, as 2.3.0 actually behaves.** The spec says argv is `<shell> -c <command>`. Measured in the private harness: the host publishes the pid; `bash -c 'sleep 30'` *execs* sleep, so ps shows `sleep 30`; a nested `sh -c '…'` loses its quotes when bash re-parses it, so ps shows `sh -c sleep 300 & echo ok`; and a shell that exits within the ~20 ms before the snapshot is still a *zombie*, whose argv is `<defunct>` or `(bash)`. So the text check accepts the `<shell> -c <command>` shape, the exec'd shape, both after normalising quotes and whitespace, and — only when the host gave a pid — an unreadable argv. The identity is carried by pid, parent, group and start time.
- **No renice** (Isaac, 2026-11-16): lowering priority of tracked processes is not an option and does not exist in the code.
- **A zombie is not alive.** `ps stat` starts with `Z` for a process that exited and has not been reaped: it does no work, must not hold a group open, and cannot be killed. `liveProcs` excludes it, so a group whose shell exited reads as a leftover even while its zombie sits in the table. Without this the orphan and idle rules never fired, because the leader "looked alive" (found in the private harness).
- **The ledger is one per service process** (`globalThis[Symbol.for("opencode.session-procs")]`, refcounted). The plugin loads once per directory and every instance hears every event, so a per-instance ledger would adopt each shell once per directory and report each reap once per directory. The newest instance rebinds the ledger's dependencies (its `ctx`), registers its host calls as a peer, and takes the scan timer over; the last release stops the timer. Events are claimed by key in a 10 s window, so one instance acts and the rest see it taken.
- **Groups persist in `ctx.storage` under `ledger/<pgid>`** — pid, group, session, shell, background, start, exit, escapees, cwd. A restart adopts back what is still there: any live member (the leader may be gone: a `&` server outliving its shell), same uid, start at or after the group's. Everything else is removed. Measured in the harness: a process that had `setsid`'d out of the pty session survived a hard service restart and was re-adopted from storage, then killed on request.
- **Background vs foreground** comes from the host's own mark: `execute.after` whose result carries a shellID (`result.output.shellID` in 2.3.0; `result.metadata.status === "running"` in 2.2.x) arrived before `shell.created` in every harness run, so the mark waits for the adoption; if it arrives later, the record is updated. It decides nothing about idling — a group whose shell is *alive* is a live background job — but it is in the ledger, the notice and the log.
- **Escapees are followed by pid.** A child whose parent is a tracked process but whose group is not (`setsid`, a detached spawn) is recorded, persisted with the group, and signalled by pid (never by its group: that group is its own). An escapee is dropped when it is no longer in the process table, or its start time predates the group.
- **CPU is a window, not a total**: the sum of `ps time=` over the group's members and escapees, delta over elapsed, percent of one core. A window whose elapsed time is zero does not divide.
- **The rules are pure** (`rules.ts`: ledger views + session facts + clock → decisions). Session facts come from `session.get`: `time.busy` after `time.idle` means running, `time.idle` is the idle clock, `parentID` selects the sub-agent window. `time.*` are Effect `DateTime.Utc` values whose milliseconds are on `epochMilliseconds`, not plain numbers (found in the harness: the first build read every session as unknown and reaped nothing).
- **No monitor, no idle reap.** The monitor plugin publishes `globalThis[Symbol.for("opencode.monitor.active")]`, a function returning `{sessionID, pgid}[]` for its running monitors; session-procs excludes those groups from matching and from every kill, refuses the idle rows for a session that has one, and treats an *absent* query as "a monitor may be running": never idle-reap. The function is process-wide because the monitor plugin also loads per directory, and each instance adds its own source.
- **Session facts are asked of the instance that can answer.** `session.get` is answered by an instance of the session's own location, while the scan loop belongs to whichever instance acquired last; every instance registers its host calls, and the scan asks the instance whose directory matches the group's cwd first, then the rest. When no instance answers, the facts are unknown and **nothing is killed from the rules** — a deleted session ends through its `session.deleted`/`session.archived` event, which needs no `session.get`.
- **The reaper re-reads the table before signalling** and keeps only processes that are still the group's: our uid, a start time at or after the group's, the group's pgid for a member, the recorded pid for an escapee; never pid 1, the service or itself, never a monitor's group. SIGTERM to the whole group (`-pgid`) and to each escapee, `killGraceSeconds`, then SIGKILL to what is left and one more look 250 ms later (a signalled process shows in `ps` until reaped). Survivors are logged and the group stays for the next scan instead of being reported again.
- **Dry run by default.** It reports what it *would* end and kills nothing; the decision is marked reported so a scan does not repeat itself. The kill guard still refuses in dry run: refusing is safe, and a pattern is dangerous whether or not this plugin would act. Off-file (`~/.config/opencode/session-procs.off`) and `enabled: false` are checked at every scan, every adoption and every guard call, and the state change is logged once.
- **The guard parses, it does not guess.** `pkill`, `killall`, and `pgrep … | xargs kill` (with `sudo`/`env`/`nohup` wrappers, assignments and options) yield a pattern; `pgrep -f` is run for the same pattern and every match is checked against this session's tracked pids. Any foreign match refuses the call with the pids and the `kill <pid>` alternative. A dynamic pattern (`$PATTERN`, a backtick, a substitution) or a form the parser does not know passes: a guard that guessed would block real work.
- **Notices never wake.** `ctx.session.synthetic({ delivery: "steer", resume: false })` waits in the inbox and arrives in front of the next prompt (measured: one model request, no turn started, both the runaway and the reap notice arrived before a user prompt in the harness). A delivery that fails stays queued, bounded at 20 scans. Each notice also goes to the alerts hub through this plugin's own RPC event (the shell-handoff pattern).
- **The log is the review surface** for the first three days of `dryRun`: one JSON line per action in `log.jsonl` (adopt, adopt-miss, escapee, shell-exited, shell-gone, runaway, reap, signal, survivors, notice, drop, restore, guard-refused, quiet, session, session-unknown). Commands are flattened and cut; nothing is executed. No rotation: only actions are written, a handful per group lifetime.

## Verified in the private harness (2.3.0, never the user's service)

Root `/private/tmp/oc-harness-procs`, own ports, its own config. Findings recorded while doing it:

- `shell.created` in 2.3.0 carries `pid`; in 2.2.7 the published `info` is the pre-pid object. Both are handled.
- Foreground and background shells are children of the harness's `opencode-pty daemon`, pid == pgid, and `lstart` agrees with `time.started` to the second.
- The pty daemon is a child of the service; monitors spawn their own group directly from the service.
- `execute.after` for a background call carries `output.shellID` and `output.pid` and arrives before `shell.created`.
- Every event is delivered once per plugin instance (three locations in the harness: three deliveries), hence the claim window and the single ledger.
- `time.busy`/`time.idle` are Effect `DateTime.Utc` (epoch on `epochMilliseconds`).

Run (options `dryRun:false`, `scanSeconds:2`, `idleMinutes:1`, `subagentIdleMinutes:1`, `runawayCpu:50`, `runawayMinutes:1`, `orphanKillMinutes:1`, `killGraceSeconds:1`):

- session A ran `sh -c 'while :; do :; done' & sleep 1; echo ok` (adopted, shell exited, loop orphaned) and a monitor `sleep 600`; the loop reached 91–100% CPU: one runaway notice, then the orphan rule ended it (`signal SIGTERM`, `reap … rule orphan`, `drop`), and the notice arrived in A in front of the next prompt with the model seeing it.
- session B ran `sleep 600` as a background job: never idle-reaped; archiving B ended it (`rule session-end`); the plain `yes` started from a normal shell, A's monitor and B's sleep were all still there after A's and C's reaps.
- session C ran `sh -c 'sleep 300 & echo ok'`: after one idle minute the leftover was ended (`rule idle`).
- session D's leftover and a restart: a graceful restart kills the pty's sessions, so the ledger restored `restore-gone` for it; a process that `setsid`'d out of the pty session survived a `SIGKILL` of the service, and the new service logged `restore … members:[78065] leaderAlive:false` (1 group) and reaped it on archive.
- `log.jsonl` has every step; `/api/session/<id>/message` shows the synthetic notices.

## Not done / upstream asks

- A host hook that says "this shell's group is yours" (pid, pgid, session) would remove the ps matching entirely.
- A graceful restart kills the pty's sessions, so a background job cannot be re-adopted across one; only processes that detached survive.
- `session.get` being location-scoped is why every instance registers its host calls; an instance-agnostic `session.get` would remove the peers.
